# Cut over to the Camba technical namespace

**Changing a Compose project name does not move its data.** For an existing installation, check ownership, copy the state with writers stopped, and validate the copy before changing the active endpoints. Keep the old containers and volumes intact. For an empty local install, use the normal [demo setup](../README.md#demo-local).

| Resource | Previous | Current |
| --- | --- | --- |
| Local Compose project | `camba-v2-demo-pg` | `camba-demo-pg` |
| Production Compose project | `camba-v2` | Explicit `CAMBA_COMPOSE_PROJECT`: `camba` only if free, otherwise a distinct project such as `camba-prod` |
| PostgreSQL application role | `camba_v2` | `camba`; production keeps the separate `postgres` administrator |
| Databases | `camba_v2`, `camba_v2_demo`, `camba_v2_demo_test`, `camba_v2_demo_seed_test` | `camba`, `camba_demo`, `camba_demo_test`, `camba_demo_seed_test` |
| Disposable legacy staging | `camba_v2_migration*` | `camba_migration*`; use a fresh isolated target |
| Development image tags | `camba-v2-dev-php-pg`, `camba-v2-dev-store-editorial` | `camba-dev-php-pg`, `camba-dev-store-editorial` |
| Volume and network prefixes | old Compose project | new Compose project; resource suffixes stay the same |
| Edge DNS aliases | `camba-v2-api`, `camba-v2-store`, `camba-v2-admin` | From explicit `CAMBA_EDGE_ALIAS_PREFIX`: for example `camba-api`, `camba-store`, `camba-admin` if free |

The existing `CAMBA_*` settings, public URLs, Laravel key and migration filenames do not change. Preserve `feat/camba-v2`, historical QA records and the old names below for identifying source/rollback resources. Do not point a new checkout at the legacy MySQL installation.

## Local Docker

1. On the intended Docker context, inspect all containers (including stopped ones), volumes and networks for `camba`, `camba-demo-pg` and `camba-v2-demo-pg`. Inspect the old containers' actual mount sources and the configured ports. A free port is not evidence that a project name or volume is free. If the destination is owned by another installation, stop the cutover; choose a distinct project name and free loopback ports instead. Use the same ignored `infra/dev/demo.env.local` and API env as the source without copying their values to Git.
2. Build the new images before stopping the old services. Block new writes, stop scheduler first and API/worker gracefully, persist Redis with `redis-cli SAVE` once its writers are stopped, then stop PostgreSQL, Redis and Mailpit. Leave the old stack stopped, not removed. Copy from read-only source volumes into **verified empty** destination volumes with the new Compose project and volume labels. Keep numerical owners, modes and symlinks. Use the same pinned PostgreSQL version for a physical copy.
3. Copy `postgres-demo`, `api-storage` (uploads, private media, refund logs and framework data), `mailpit-data` and the Redis container's actual `/data` mount (historically anonymous; now `redis-data`). The existing host bind `api/storage/logs/pagos` stays in place. Vendor and build caches are not sources of business data. Compare source/destination file manifests before starting services and verify the original volumes still exist.
4. Start only the copied PostgreSQL volume in the new project. From the maintenance database `postgres`, verify the old databases exist and the target names do not. Rename the three demo databases with `ALTER DATABASE old RENAME TO new`; rename the application role from a **different** administrator session. On the old demo cluster `camba_v2` may be the only superuser: create a temporary local administrator on the copied cluster, use it for the rename, then drop it using the renamed role. Confirm the existing SCRAM credential works over TCP; an MD5 verifier must be reset securely if PostgreSQL clears it on rename. Do not recreate the schema or rewrite the `migrations` table. [PostgreSQL role rename](https://www.postgresql.org/docs/18/sql-alterrole.html) · [Database rename](https://www.postgresql.org/docs/18/sql-alterdatabase.html).
5. Start the new local stack with the same loopback ports (normally API 8000, Store 4200, Admin 4300, Mailpit 8025). Check schema history, product/order counts and representative image routes, Redis health, Mailpit message count, API readiness and the worker/scheduler health checks. Use a separate test project and `camba_demo_test` for PHPUnit, never the live demo.

Rollback **before reopening writes**: stop the new project, then start the existing old containers without rebuilding or applying the new Compose configuration to them. The payment log bind is shared, so never run both schedulers or workers against it. Once the new environment accepts writes, do not switch back to the old snapshot without a separate data-reconciliation plan.

## VPS cutover — not executed from development

1. **Inventory with separately authorized access.** Record Compose ownership and host labels, mounted volumes, PostgreSQL version/database/roles, running release manifest and the proxy's active DNS targets. If `camba` or any default `camba-*` edge alias belongs to the other installation, leave it alone. Choose both a distinct project (for example `camba-prod`) and a distinct alias prefix (for example `camba-prod`). Keep the new stack off the shared edge network during preparation.
2. **Prepare the release entry point before replacing anything.** Verify the running entry point still resolves the old approved project using the old Compose/env/overlay. If adopting the new executor early, leave that configuration installed: when the original Compose declares `name: camba-v2`, an unchanged wrapper still targets it. Explicitly configure and verify the old project in custom wrappers first. Stage the new executor, Compose, env and edge configuration separately, using a separate release state directory for a parallel stack; set the new wrapper project explicitly and check it against the new Compose project before switching the active entry point. Never combine a new Compose/edge file with an old wrapper's implicit target.
3. **Preserve rollback material.** Keep the old Compose/release/proxy files and the protected Laravel key. In the approved maintenance window, pause incoming traffic/jobs and drain writers. Back up and verify recovery of PostgreSQL, Redis, public media, private files, `payment-logs` and `refund-logs`. If the old server still writes historical `refounds` in container layers, copy files from each old PHP role before recreating any of them; follow [the refund log import runbook](REINTEGROS_LOG.md). Do not use `down -v`.
4. **Restore to a distinct project and storage.** Create/restore the new volumes, using the matching PostgreSQL major and appropriate verified backup/restore or cold-copy procedure. On the restored cluster, inspect for destination role/database collisions. From `postgres` as the separate administrator, rename the old database and application role to `camba`, retaining ownership and the applied migration records; verify credentials and non-superuser privilege. If the source is MySQL, use its separately reviewed migration instead of copying PostgreSQL volumes or renaming the old database.
5. **Validate privately before switching.** Use the immutable CI digests and protected runtime files. Set `CAMBA_COMPOSE_PROJECT` to the approved project in both the protected Compose config and the release executor's environment. Set the reserved `CAMBA_EDGE_ALIAS_PREFIX` explicitly in Compose config; preflight with `docker compose ... config --quiet` without logging the resolved environment. Compare migration history, counts and stock, uploads/private media, payment/refund logs, Redis queue and application/fiscal logs. Verify Admin, Store/API, worker and scheduler; check HTTPS/cookies, proxy headers, and webhook routing without real test charges.
6. **Switch only the approved vhosts.** Validate that none of the three new aliases is already held on the real edge network, then attach the new stack with the edge overlay and point the proxy to the chosen prefix. Preserve public domains, paths and webhook query strings. Do not restart or route traffic to the legacy project by mistake. Keep old volumes and proxy config until the operator accepts the cutover. If rolling back before writes resume, detach the new upstreams and restore the old proxy targets/stack; after writes resume, preserve and reconcile new data before any rollback.

See [deployment inputs](RELEASE.md), [PostgreSQL first installation](POSTGRESQL_CUTOVER.md), and the [Docker Compose volumes reference](https://docs.docker.com/reference/compose-file/volumes/).
